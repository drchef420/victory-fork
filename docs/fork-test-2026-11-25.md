# Test runs on a 16 GB PC (2026-11-25)

Branch `test-run` with fxceless/victory-fork `main` (0b0074e) merged. PC: RTX 3060 Ti
8 GB (32-lane waves; a second one unused), 16 GB of memory, Windows 11.

## Ray-tracing structure builder

`VICTORY_HOST_WAVE=32 VICTORY_WAVE_WHY=1 victory translate <game> --pipelines`:
52 builder programs, 29 at any wave size, 20 at a fixed wave size (32 lanes:
fine on this GPU), 3 stopped, all with `emit: a first-lane read where not every
lane runs` (`emit/lower.rs`, `v_readfirstlane_b32` in a half-wave pair):

- `XboxBvhBuilder.dll@0x99160 #dc78c5de69c7c155` (at 0x258)
- `XboxBvhBuilder.dll@0x9a830 #322ed4ad832bdea6`
- `XboxBvhBuilder.dll@0x9be80 #d441b097704ab616`

With `VICTORY_FIRSTLANE_OWN=1` (the host wave's own first lane; exact only when
the value is the same in every lane of the console wave) the translate run
reports all 52 ready and 0 stopped, so the all-or-none rule would let the
builder run. A game run with `VICTORY_BVH_BUILDER=1 VICTORY_FIRSTLANE_OWN=1
VICTORY_BVH_QUARANTINE=1` ended at 1 min 47 s, before any builder dispatch, in
the title's own crash path (`+0x2215c35`, the caller of the usual `+0x23cf683`)
with no stall before it and 6.5 GB of memory free. One run only: not known
whether a switch caused it. Open: show that the value read is the same across
the console wave (the uniformity analysis), so the read is exact without the
switch.

## The crash a few minutes in

Every run (5 of 5 without the builder switches) ended 2.5 to 5 minutes in, on
the loading screens or the opening, the same way: one frame takes 20 to 45 s,
then the title writes to address 0 at `victory-image+0x23cf683` (`rax = rbx =
0`, the same registers each time), its Breakpad uploader starts (blocked by
`net`), and the process ends. A deliberate stop by the title's hang check after
a long stall, not a bug at that address.

The stall is the PC paging. Counters sampled every 5 s through the stall: up to
31,000 pages a second read back from disk (100-130 MB/s), 300-1,000 MB of memory
available, then the process nearly idle (8-14 % of one core) until the title
stops. During the stall VIctory's own periodic status block, normally written
in 50 ms, takes 40 s (one line every few seconds; lines out of order).

- With the paging file managed by Windows (5.7 GB) the commit left was under
  1 GB from the start and grew in steps during the stalls; a fixed 32 GB
  paging file left 23 GB to commit and the stalls stayed: commit is not the
  limit, physical memory is.
- `VICTORY_LEVELS_ON_DEMAND=1`: 0.8-1.2 GB of the card not allocated; the stall
  and crash are unchanged.
- The title never called `XMemGetWorkingSetStatistics` (no `the title asks how
  much memory it uses` line), so `VICTORY_TITLE_USED=own` cannot matter here.

Memory map (diagnostics build, at the stall): the title's heaps 4.6 GB, views of
the title's pages 6.0 GB (1.8 GB resident), the title's page pool 6.2 GB mapped
(0 resident), process heap 0.57 GB, write-combined buffers 2.8 GB (0.44
resident), other private allocations 2.7 GB (three of 1 GiB: 1.9 GB), files
1.1 GB, programs 0.5 GB. Process private 10.5-11.8 GB, working set 7-8 GB; the
card's driver also kept 4.4-5.0 GB of the PC's memory in use as shared memory
(the 8 GB card at 85 % of its budget), which comes out of the same 16 GB.

A 32 GB PC with a 12 GB card is the next test machine: see below.

## A run on a 32 GB PC

PC: RTX 5070 12 GB (the game's card, by a per-app graphics preference for
`victory.exe`: Windows' default would have been the RTX 3060 beside it, which
drives the main display), 32 GB of memory, Core Ultra 7 270K Plus. The
paging file was set to a fixed 32 GB but the PC had not restarted, so the run
had the earlier one: 7.2 GB allocated, 2.5 GB at its peak, a commit limit of
34-39 GB. `tools\fork-test.ps1`, no switches, commit 9954cc6.

- No crash and no stall: 43 minutes (22:49 to 23:32 UTC, 47,223 frames), into
  the game and well past the opening, ended by the player closing the window.
  Every run on the 16 GB PC ended 2.5 to 5 minutes in, which fits the paging
  account above: with the memory, the stall does not happen.
- 5 frames a second most of the time (195-215 ms a frame, 2,000-3,300 draws a
  frame), dips to 1-3 (350-1,040 ms).
- What the player saw: the rooms have their walls but the walls' textures are
  black; a guard was only a shadow; many characters, the player's included,
  had no faces, only eyeballs and teeth.
- Pipelines the title goes without: device method `0x1c8` failed at least
  16,384 times and `0x218` at least 2,048 (the log keeps powers of two), with
  `E_NOTIMPL` (`device.rs`, `unknown_pipeline`). The ordinary path made 2,195
  pipelines. Many more of the title's pipelines are missing than are made,
  which can account for what is missing on screen; not shown which draws use
  them. Next: work out the two descriptions (logged in the run) and make
  those pipelines.
- Shaders the translator still leaves out (`builder.txt`): 195 with an address
  in an SGPR that is no root parameter, 40 with a descriptor chosen by control
  flow (among them `PS_TexturedDeferred`), 27 the driver refused ("The
  parameter is incorrect"), 10 with a hardware SGPR input (among them
  `PS_PedTexturedCutOutTint`, a character shader), 29 SM5 or older.
- The builder report is the same as on the 16 GB PC: 52 programs, 3 stopped
  on the first-lane read.

### The builder run on the 32 GB PC

`tools\builder-run.ps1` (`VICTORY_BVH_BUILDER=1 VICTORY_FIRSTLANE_OWN=1
VICTORY_BVH_QUARANTINE=1`), same PC and commit, RTX 5070. The loading screens
ran at 30 frames a second (10 draws); the builder started when the loading
ended, at frame 12,394, 7 minutes in (23:45:11.8 UTC: `the ray-tracing
structure builder runs: all of its programs have host pipelines
pipelines=53`), and the title crashed 11 s later, as the player saw it
("crashed as soon as the loading finished").

- 0.8 s after the builder's first dispatch: `title memory by address: no
  number left for another copy; its pages read zeros COPIES=1023`
  (`memory.rs`). The builder named more than 1,023 buffers within its first
  frame (the module's note expects about 50 a frame for the opening
  cutscene); every page past that reads 0 and its stores are dropped, so the
  structures it built from them are wrong. The run without the builder never
  reached this limit.
- The crash: `0xc0000005` at `victory-image+0x35a4245`, a read of
  `0xffffffffffffffff`, called from `+0x13a78` ... `+0x221c29c`,
  `+0x2215eca` (the thread of the earlier crash path `+0x2215c35`). Not a
  hang check this time: no stall before it, 4.5 GB free. Not shown that the
  zeroed pages caused it, but it is the first thing to rule out.
- A driver error reached the system's event log 7 s into the run, before the
  builder (the driver watch turned the paths under suspicion off); its cause
  is not in the log.
- Done after the run: `COPIES` is 8,191 (the dynamic part of the view heap
  has 262,144 slots), and `title memory by address: copies numbered so far`
  is logged at 64, 128, 256 ... copies (`builder-run.ps1` puts those lines in
  `summary.txt`).

### The second builder run, with 8,191 copies

Same switches, PC and card. The loading was shorter this time (the host
pipeline library loaded 2,170 pipelines): the builder started at frame 1,840,
1 min 47 s in (00:38:16.5 UTC), and the title crashed 4 s later.

- The copy limit was not the cause: 256 copies numbered by then (the log has
  64, 128, 256), far under 8,191, and no `no number left` line.
- Nine title threads faulted in the same second (`crashes.log`, process
  5712), all on the same thread base (`+0x221c29c`, `+0x2215eca`), at six
  places (`+0x8f92a` three times, `+0x4e50a98` twice, `+0x4e335b4` twice,
  `+0x52ecfd9`, `VCRUNTIME140+0x1cca7`), nearly all reading
  `0xffffffffffffffff`. In six of them `rax` holds two floats of infinity:
  `0x7f8000007f800000` (+inf, +inf), `0xff800000ff800000` (-inf, -inf),
  `0xff8000007f800000`: the values bounds start at before anything is added
  to them (an empty box). So builder output reached memory where the title
  keeps pointers, as in run 98 before the quarantine existed.
- Why the quarantine let it through: `VICTORY_BVH_QUARANTINE=1` turned off
  the copy back for root views and for title memory by address
  (`draw.rs`, `writes`), but not for unordered access views in descriptor
  tables, which `readable` marks written whenever the shader can store.
  Fixed after the run: a `QUARANTINED` flag set while a quarantined stage's
  tables are walked keeps those out too. Not yet run.
- The frame the builder started in took 3.4 s (880 ms preparing, 1,454 MB of
  copies sent up, 31 MB copied back).

### The third builder run, with the table views quarantined too

Same switches, the build with the `QUARANTINED` fix (`victory.exe` built
19:40:35 local, the run started 19:42:41). The builder started at 00:43:46
UTC, 1 min 4 s in, numbered 512 copies, and the title crashed 4 s later: 13
faults in process 26204, again across the title's worker threads, at
`+0x8f92a` (6), `VCRUNTIME140+0x1c78b` (2), `+0x4684e7` (2), `+0x1d75a9`,
`+0x1d75ac`, `+0x25dbe4a`; again mostly reads of `0xffffffffffffffff`, and
again infinities in registers (`0xff800000ff800000` twice,
`0x7f8000007f800000`, `0xff800001ff800080`, `0xfc000000fc000000`).

- The fix took something out: the frame the builder started in copied back
  8.3 MB, against 30.9 MB the run before. What is left is not split by
  pipeline in the log, so it is not known whether any of it is the
  builder's.
- The other reading of the same crash: with the quarantine the title gets
  none of the builder's results back (`builder_quarantined`'s own note:
  "the title also reads results back (sizes, counters) and gets none"). A
  value the builder should have written over, left at -1, read as an
  address is exactly `0xffffffffffffffff`; the infinities could then be the
  title's own empty bounds next to it.
- Next: the same run without the quarantine
  (`tools\builder-run.ps1 -NoQuarantine`). If it gets further, the
  quarantine was what crashed these runs; if it crashes the same way, the
  builder's output is wrong.

### The builder without the quarantine

`tools\builder-run.ps1 -NoQuarantine` (`VICTORY_BVH_BUILDER=1
VICTORY_FIRSTLANE_OWN=1`), same build. The builder started at 00:48:57 UTC,
2 min 33 s in, numbered 512 copies, and the title crashed 5 s later the same
way: 13 faults in process 25952, 8 of them at `+0x8f92a`, the rest at
`VCRUNTIME140+0x1c78b` (2), `+0x4e335b4`, `+0x52ec9f5`, `+0x8655c1`; `rax`
`0x7fffffff00000000` five times, infinity pairs five times. The frame it
crashed in copied back 56.9 MB (8.3 MB with the quarantine).

- So the quarantine is not what crashes these runs: with it and without it
  the title fails the same way within seconds of the builder starting, and
  without the builder (run 1) it plays for 43 minutes past the same point.
- What the faults are: a read reported at `0xffffffffffffffff` is how
  Windows reports a general-protection fault, an access through an address
  that is no address at all (not canonical). `0x7f8000007f800000`,
  `0xff800000ff800000` and `0x7fffffff00000000` are such values. The
  title's threads use words of empty bounds, or of +-largest, as pointers:
  memory where the title keeps pointers holds bounds.
- Open: where those words come from. The quarantine keeps the builder's
  stores out of title memory on the paths it knows of, and the crash does
  not change with it, so either they reach title memory another way (a host
  copy the builder wrote into, later declared written by another shader and
  copied back whole; a copy in place, whose shaders write title memory
  itself) or the title itself writes them because of what the builder gives
  it.
- Done after the run: `VICTORY_BOUNDS_WATCH=1` (`host.rs`, `bounds_watch`)
  looks at every copy back of what shaders wrote, on all four paths, just
  before the bytes go into title memory, and logs each one that carries an
  empty-bounds word: the frame, the range and the first such address.
  `builder-run.ps1` now sets it and puts those lines in `summary.txt`.
  Copies in place are not seen by it (their shaders write title memory
  directly). Next: run the builder once more, with or without the
  quarantine, and match the logged addresses to the addresses in the
  crashed threads' registers.

## Notes on the tools

- `VICTORY_STACKS` can stall the process: in one run the dump suspended a title
  thread and did not get past it for 44 s (until the title's hang check fired),
  so a run with it does not tell a natural stall from its own.
- `tools/fork-test.ps1` now notes the PC's memory and paging file in
  `summary.txt` and warns under 30 GB or with a paging file Windows manages.

### The builder with the bounds watch, and the save

`tools\builder-run.ps1` (quarantine on) with `VICTORY_BOUNDS_WATCH=1`. The
builder started at 00:53:55.9 UTC, 1 min 6 s in; the title crashed about
4 s later, 13 faults in process 33024, as before.

- At frame 1,574, 3.5 s after the builder started, copies back into title
  memory carried empty-bounds words: the first 64 logged (all within 13 ms),
  from hundreds to thousands of such words per 64 KiB, in ranges at
  `0x742dd0000`-`0x742ea0000`, `0x7694...`, `0x76c4...`, `0xb0a4...`,
  `0xb6ae...`, `0xb8bf...`, `0xcdff...`-`0xce03...`. None before it, in
  the loading frames. That frame compared 645.7 MB in 161 ranges of
  windows outside buffers (the 4 MiB windows), against 2.9 MB of buffers.
- The crashed threads' object pointers (`rbx`, `rsi`, `rdi`) are at
  `0xd35...`-`0xd39...`, `0xdfd1...`, `0xdfd5...`, `0xe14...`: none of the
  64 logged ranges, which are the first 64 of more (the next line would be
  the 1,025th). Not matched yet.
- A confound: the first run (no switches) started without a save, from the
  beginning; it saved the player at 18:11:59 (`saves/.../Player~...`,
  near the counselor's office). Every builder run since loaded that save,
  and the builder starts as that load ends. No run has loaded that save
  without the builder, so what crashes may be the load of that place, not
  the builder. `builder-run.ps1 -NoBuilder` is that control: the same save,
  only the bounds watch on. If it plays, the builder is what crashes; if it
  crashes the same way, the save's place does, and whether its empty-bounds
  copies back come without the builder too tells the rest.

Done after this: the player save deleted (the settings profile left in
place), so the next run starts from the beginning, as the first run did.
A builder run from there is the comparison with the first run: the same
start, the builder the only difference.
