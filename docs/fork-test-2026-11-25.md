# Test runs on a 16 GB PC (2026-11-25)

Branch `test-run` with fxceless/victory-fork `main` (0b0074e) merged. PC: RTX 3060 Ti
8 GB (32-lane waves; a second one unused), 16 GB of memory, Windows 11.

## Ray-tracing structure builder

`VICTORY_HOST_WAVE=32 VICTORY_WAVE_WHY=1 victory translate <game> --pipelines`:
52 builder programs, 29 at any wave size, 20 at a fixed wave size (32 lanes:
fine on this GPU), 3 stopped, all with `emit: a first-lane read where not every
lane runs` (`emit/lower.rs`, `v_readfirstlane_b32` in a half-wave pair):

- `XboxBvhBuilder.dll@0x99160 #dc78c5de69c7c155` (at 0x258)
- `XboxBvhBuilder.dll@0x9a830 #322ed4ad832bdea6`
- `XboxBvhBuilder.dll@0x9be80 #d441b097704ab616`

With `VICTORY_FIRSTLANE_OWN=1` (the host wave's own first lane; exact only when
the value is the same in every lane of the console wave) the translate run
reports all 52 ready and 0 stopped, so the all-or-none rule would let the
builder run. A game run with `VICTORY_BVH_BUILDER=1 VICTORY_FIRSTLANE_OWN=1
VICTORY_BVH_QUARANTINE=1` ended at 1 min 47 s, before any builder dispatch, in
the title's own crash path (`+0x2215c35`, the caller of the usual `+0x23cf683`)
with no stall before it and 6.5 GB of memory free. One run only: not known
whether a switch caused it. Open: show that the value read is the same across
the console wave (the uniformity analysis), so the read is exact without the
switch.

## The crash a few minutes in

Every run (5 of 5 without the builder switches) ended 2.5 to 5 minutes in, on
the loading screens or the opening, the same way: one frame takes 20 to 45 s,
then the title writes to address 0 at `victory-image+0x23cf683` (`rax = rbx =
0`, the same registers each time), its Breakpad uploader starts (blocked by
`net`), and the process ends. A deliberate stop by the title's hang check after
a long stall, not a bug at that address.

The stall is the PC paging. Counters sampled every 5 s through the stall: up to
31,000 pages a second read back from disk (100-130 MB/s), 300-1,000 MB of memory
available, then the process nearly idle (8-14 % of one core) until the title
stops. During the stall VIctory's own periodic status block, normally written
in 50 ms, takes 40 s (one line every few seconds; lines out of order).

- With the paging file managed by Windows (5.7 GB) the commit left was under
  1 GB from the start and grew in steps during the stalls; a fixed 32 GB
  paging file left 23 GB to commit and the stalls stayed: commit is not the
  limit, physical memory is.
- `VICTORY_LEVELS_ON_DEMAND=1`: 0.8-1.2 GB of the card not allocated; the stall
  and crash are unchanged.
- The title never called `XMemGetWorkingSetStatistics` (no `the title asks how
  much memory it uses` line), so `VICTORY_TITLE_USED=own` cannot matter here.

Memory map (diagnostics build, at the stall): the title's heaps 4.6 GB, views of
the title's pages 6.0 GB (1.8 GB resident), the title's page pool 6.2 GB mapped
(0 resident), process heap 0.57 GB, write-combined buffers 2.8 GB (0.44
resident), other private allocations 2.7 GB (three of 1 GiB: 1.9 GB), files
1.1 GB, programs 0.5 GB. Process private 10.5-11.8 GB, working set 7-8 GB; the
card's driver also kept 4.4-5.0 GB of the PC's memory in use as shared memory
(the 8 GB card at 85 % of its budget), which comes out of the same 16 GB.

A 32 GB PC with a 12 GB card is the next test machine.

## Notes on the tools

- `VICTORY_STACKS` can stall the process: in one run the dump suspended a title
  thread and did not get past it for 44 s (until the title's hang check fired),
  so a run with it does not tell a natural stall from its own.
- `tools/fork-test.ps1` now notes the PC's memory and paging file in
  `summary.txt` and warns under 30 GB or with a paging file Windows manages.
